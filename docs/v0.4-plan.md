# v0.4 — Rekognition + Marengo hybrid for entity reID

Replaces the bespoke gdino + DeepSORT + TAO + Titan pipeline with a
Rekognition-primary, Marengo-fallback hybrid. Based on the 4-way eval at
`eval/entity-reid/results/ground_truth.suggested.md`.

## TL;DR

- **Rekognition Faces** as primary face-retrieval backend (best MRR
  0.77 and recall@5 0.47 on the trailers KS eval).
- **Marengo image query** against the existing `clips` index as
  fallback for Rekognition misses (no new infra; uses the already-
  populated production index).
- **Delete** the entire gdino/Titan stack — operationally heavy (GPU
  endpoint, Step Function, 3 lambdas) for only +0.06 recall@20 over
  Rekognition.
- **Auto-trigger** Rekognition IndexFaces on every upload. The bespoke
  pipeline was a manual batch job that no operator ever fired, so every
  KS shipped with empty entity-reID indexes. Don't repeat the mistake.

## Architecture

```
upload (UI Library) → presigned PUT → S3 clips/<asset>.mp4
                                          │
                                          ▼
                                  embed_clip_start
                                  ┌────────┬────────┐
                                  ▼        ▼        ▼
                          MediaConvert  Marengo  asset_profile
                                  │
                                  ▼ (HLS done)
                              hls_finalize
                                  │
                                  ▼ (NEW: triggers IndexFaces)
                              index_faces  ←─── new lambda
                                  │
                                  ▼
                       Rekognition collection
                       (ExternalImageId = asset_id)


agent tool: find_by_image(reference_url, ks_id, k)
  1. Rekognition SearchFacesByImage (threshold 80) ──► face matches
  2. If hits < k OR face miss ► Marengo image embed (async, 3-5s)
     ──► QueryVectors against clips index ──► visual matches
  3. Merge, dedupe by asset_id, return top k
```

## Implementation order

Safer than parallel: do the additive work first, validate, then delete.

1. **Stand up Rekognition collection + IndexFaces lambda** (no auto-trigger yet)
   - Terraform: collection, IAM, lambda
   - Test: manual lambda invocation on one asset
2. **Backfill existing KSes** by manual SF-like batch (a one-shot script
   that iterates assets table per ks_id and invokes IndexFaces)
3. **Add `find_by_image` agent tool** (Rekognition + Marengo hybrid)
   - Keep the old `find_entity_by_image` tool in place but unused, for rollback
   - Update system prompt to use the new tool
   - Build + push new agent image, bump `agent_image_tag`, deploy
   - Smoke-test via the SPA
4. **Wire auto-trigger** for IndexFaces on `hls_finalize` completion
   - EventBridge rule fires the lambda when HLS bundle is ready
   - Test by uploading a new asset
5. **Delete bespoke stack** in one Terraform commit
   - Remove `entity_reid_*` lambdas
   - Remove `sagemaker-async-endpoint.tf`
   - Remove `step-functions.tf` + ASL
   - Remove `agent/expert-models/gdino/`
   - Remove unused IAM / outputs / S3 Vectors indexes
   - Drop `find_entity_by_image` tool from agent (the rollback safety net)
6. **UI cleanup** — remove Titan/Phase-3 mentions from LiveArch components
7. **Release v0.4** — release notes, tag, GitHub release artifact

## Decisions

1. **Collection scope: per-KS.** Created on first IndexFaces call (the
   ingest path lazy-creates if absent). Deleted in the `kb_admin`
   delete-KS handler. Collection id convention: `<stack-fqname>-ks-<ks_id>`.
   The agent's `find_by_image` derives the collection id from the
   `knowledge_store_id` argument — no DDB join needed.
2. **Frames per asset: 4.** Evenly spaced across the HLS thumb capture
   sequence (matches the eval). One IndexFaces call per frame, so
   ~4 × ~2-3 faces = ~10 face vectors per asset.
3. **Marengo embed cache: yes.** Key by `sha256(image_bytes)` →
   `s3://<clips>/embed-cache/marengo/<hash>.json`. ~10 LoC inside the
   agent tool — eliminates the 4 s async-invoke cost on repeat queries
   in the same producer session.
4. **Backfill: script.** Lift `eval/entity-reid/pipelines/rekognition_
   faces.py:ingest()` into `scripts/backfill_rekognition.py` and run
   once per existing KS. Excluded from the release zip (joins
   `scripts/` already in EXCLUDE_PATHS).

## Rollback plan

Keep the old `find_entity_by_image` tool through step 5; delete it in
the same commit that removes the bespoke infrastructure. If the new
tool misbehaves in steps 3-4, revert the agent image (the prior tag
still works against the still-empty Titan indexes — degraded but not
broken).

**Total: ~4 days.**

## Migration risk

**Low.** The bespoke stack we're deleting has never produced data in any
production KS (verified — the entity-thumbs/entity-patches indexes were
empty across all 5 demo KSes before the eval). Deleting it doesn't
break anything live. The new lambda + collection don't conflict with
existing infrastructure.

The one real risk: the `find_by_image` agent tool is new. If the hybrid
routing has a bug, the agent's image-grounded search degrades or fails.
Keeping the prior tool through step 5 as a rollback is the mitigation.
